# Wisenet UDP Native Messaging Host

Manifest V3 extensions cannot use `chrome.sockets.udp` (it was a Chrome
Apps API and Chrome Apps have been discontinued). This directory contains
a small [native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)
host that performs the Wisenet device-discovery UDP broadcast on behalf of
the extension:

- broadcasts the discovery payload to `255.255.255.255:7701`
- listens for device replies on UDP port `7711`
- parses each reply and relays it to the extension as a plain device object

The reply parsing uses [`../../sunapi/response.ts`](../../sunapi/response.ts)'s
`UdpResponse.parse().toLegacyDeviceObject()` — the same parser
[`../../nodejs/udpDiscovery.ts`](../../nodejs/udpDiscovery.ts) uses for its own
standalone Node.js discovery (`src/sunapi/` is a directory shared by both of
them; see [`../../sunapi/README.md`](../../sunapi/README.md) for why it isn't
inside either one). The extension (`scripts/socket.ts`) used to parse the
raw 334-byte SUNAPI struct itself; it now just receives the already-parsed
object, so there's a single implementation of the wire format instead of
two that could drift apart.

The discovery **request** is likewise built with
[`../../sunapi/request.ts`](../../sunapi/request.ts)'s `UdpRequest` (§3.4.1,
`nMode = DEF_REQ_SCAN_EXT`) rather than a hardcoded packet — see
`wisenet-udp-host.js`'s `buildDiscoveryPacket()` comment for a documented
tradeoff worth knowing about: this spec opcode has previously been
observed to draw replies from a broader, less targeted part of the
network than the legacy opcode it replaced. If discovery results ever
look wrong (devices that shouldn't be there), that's the first thing to
suspect — see that comment for how to revert.

## Requirements

- [Node.js](https://nodejs.org/) available in `PATH`

## Install

0. From the repository root: `npm install && npm run build` — this
   compiles `wisenet-udp-host.ts` and assembles `dist/chrome-extension/`,
   including a copy of this directory at `dist/chrome-extension/native-host/`.
   Everything below happens **inside `dist/chrome-extension/native-host/`**,
   not this source directory.
1. Load the extension (`chrome://extensions` → Developer mode → *Load
   unpacked* → `dist/chrome-extension`) and copy its **extension ID**.
2. Register the host for the current user (run from
   `dist/chrome-extension/native-host/`, or use the full path):

   **Windows**

   ```bat
   powershell -ExecutionPolicy Bypass -File install-host.ps1 <extension-id>
   ```

   **macOS / Linux**

   ```sh
   ./install-host.sh <extension-id>
   ```

3. Restart Chrome, open the extension window, and click **Start Discovery**.

`install-host.ps1` writes the host manifest to
`%LOCALAPPDATA%\WisenetIPInstaller\native-host\com.wisenet.ipinstaller.json`
and points `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.wisenet.ipinstaller`
at it — deliberately **not** next to this script: when run from
`dist/chrome-extension/native-host/` (the built copy, not this checked-in
source), that directory gets wiped and recreated by every `npm run build`,
which would silently delete the manifest and leave the registry pointing
at a file that no longer exists. `install-host.sh` writes the manifest
into Chrome's per-user `NativeMessagingHosts` directory, for the same
reason (a stable, non-`dist/` location). For Microsoft Edge, use the same
manifest under `HKCU\Software\Microsoft\Edge\NativeMessagingHosts`
(Windows) or `~/.config/microsoft-edge/NativeMessagingHosts` (Linux) /
`~/Library/Application Support/Microsoft Edge/NativeMessagingHosts` (macOS).

**`dist/` is generated and gitignored** — `npm run clean` (or a fresh
clone) removes it entirely, including `wisenet-udp-host.js`/`.bat` (the
actual host process the manifest's `path` points at). Re-run
`npm run build` before starting discovery again after that; the
registration itself (the manifest + registry entry, both outside `dist/`)
survives a rebuild and only needs re-running the install script again if
the extension ID changes or you move/re-clone the repo to a new path.

## Files

| file | purpose |
| --- | --- |
| `com.wisenet.ipinstaller.json.template` | Checked into git. The manifest shape with `@HOST_PATH@` / `@EXTENSION_ID@` placeholders — copy and fill this in, don't edit a generated file by hand. |
| `com.wisenet.ipinstaller.json` | Generated by the install scripts from the template above — but written to a stable location *outside* this directory (see the Install section above), not here, so there's nothing generated in this directory to gitignore. It bakes in an absolute path and your local extension ID, both specific to your machine/checkout, so it can't be shared or committed. |
| `wisenet-udp-host.js` / `wisenet-udp-host.bat` | The actual native messaging host process (the `.bat` just launches the `.js` with `node` on Windows). |

If the installed manifest ever goes missing or looks wrong, just re-run `install-host.ps1` / `install-host.sh` — it's regenerated from the template every time, so there's nothing to lose.

## Manual setup (without the install scripts)

The install scripts above are just a shortcut for filling in the template
and registering it with the browser. If you'd rather do it by hand (or
need to debug why the scripts aren't producing what you expect), the
steps are:

1. Copy `com.wisenet.ipinstaller.json.template` to a new file named
   `com.wisenet.ipinstaller.json` (in this directory, or anywhere else —
   the browser only cares about the path in the next step, not where the
   file physically lives).
2. Edit the copy and replace both placeholders:
   - `@HOST_PATH@` → the **absolute path** to `wisenet-udp-host.bat`
     (Windows) or `wisenet-udp-host.js` (macOS/Linux). On Windows, JSON
     needs backslashes escaped: `"C:\\path\\to\\native-host\\wisenet-udp-host.bat"`.
   - `@EXTENSION_ID@` → the extension's ID from `chrome://extensions`
     (Developer mode must be on to see it). To let more than one
     extension use this host, turn `allowed_origins` into multiple
     entries:
     ```json
     "allowed_origins": [
       "chrome-extension://<first-extension-id>/",
       "chrome-extension://<second-extension-id>/"
     ]
     ```
3. Tell the browser where that file is:
   - **Windows**: create/set the registry value
     `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.wisenet.ipinstaller`
     (default value) to the **absolute path of the JSON file** from step 1
     — not the extension, the manifest file itself. For Edge, use
     `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\com.wisenet.ipinstaller`
     instead.
   - **macOS/Linux**: place the JSON file at
     `~/.config/google-chrome/NativeMessagingHosts/com.wisenet.ipinstaller.json`
     (or the Edge/macOS paths listed above) — for these, the *filename*
     itself (not a registry value) is what the browser looks up, so it
     must be named exactly `com.wisenet.ipinstaller.json`.
4. Restart the browser (native messaging host registrations are only read
   at browser startup) and click **Start Discovery**.

Whichever way you set it up, `com.wisenet.ipinstaller.json` itself must
never be committed — see the **Files** section above (and prefer a
location outside this repo entirely, like the install scripts use, so an
`npm run build`/`npm run clean` can never delete it out from under the
registration).

## Protocol

Extension → host:

| message | effect |
| --- | --- |
| `{ "command": "start", "receivePort": 7711, "sendPort": 7701, "broadcastAddress": "255.255.255.255" }` | bind + broadcast (the discovery request payload is built in by the host itself, not sent by the extension) |
| `{ "command": "broadcast" }` | re-send the discovery payload |
| `{ "command": "stop" }` | close the socket |
| `{ "command": "httpRequest", "requestId", "method", "url", "headers", "body", "username", "password" }` | performs a SUNAPI HTTP(S) request on the extension's behalf, bypassing browser TLS certificate validation (`rejectUnauthorized: false`), including the Digest-auth challenge/response round if the device asks for one. Used by `src/shared/scripts/nativeSunapiClient.ts` for cameras/NVRs with a self-signed certificate — restricted to private/loopback/link-local IP-literal targets only. Full spec: [`../../../docs/native-https-proxy/SRS.md`](../../../docs/native-https-proxy/SRS.md). |
| `{ "command": "wsOpen", "connectionId", "url" }` | opens a `ws://`/`wss://` connection to the RTSP-over-WebSocket streaming server on the extension's behalf, also bypassing browser TLS validation — the video-streaming counterpart to `httpRequest`. Same IP-literal restriction. Used by `src/shared/scripts/nativeWebSocketTransport.ts`. |
| `{ "command": "wsSend", "connectionId", "data" }` | sends one binary frame (base64) on an already-open connection |
| `{ "command": "wsClose", "connectionId" }` | closes the connection |

Host → extension:

| message | meaning |
| --- | --- |
| `{ "type": "started", "receivePort": 7711 }` | socket bound, broadcast sent |
| `{ "type": "device", "device": {...} }` | a parsed camera/NVR reply — same shape as `UdpResponse.prototype.toLegacyDeviceObject()` (`../../sunapi/response.ts`): `chMac`, `chIP`, `chDeviceName`, `DDNSURL`, `nHttpPort`, `url`, `rtspUrl`, etc. Replies that aren't a scan response (RSA key exchange, password-apply, ...) are parsed and dropped, not relayed. |
| `{ "type": "error", "message": "..." }` | something failed (e.g. port in use) |
| `{ "type": "httpResponse", "requestId", "status", "statusText", "headers", "body" }` | the `httpRequest` command's final response (after any Digest retry) |
| `{ "type": "httpError", "requestId", "message" }` | the `httpRequest` command failed (rejected non-private-IP target, connection error, etc.) |
| `{ "type": "wsOpen", "connectionId" }` | the streaming connection is open |
| `{ "type": "wsMessage", "connectionId", "data" }` | one binary frame (base64) from the streaming connection |
| `{ "type": "wsError", "connectionId", "message" }` | the streaming connection failed |
| `{ "type": "wsClose", "connectionId", "code", "reason" }` | the streaming connection closed |

## Test without a device

With the host running (extension connected), `sender.py` in the repository
root can simulate a camera reply on the loopback interface.

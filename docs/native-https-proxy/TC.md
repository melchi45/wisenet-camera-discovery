# TC — Native-Host HTTPS Proxy for Untrusted Camera Certificates

| | |
|---|---|
| Related docs | [PRD](PRD.md) · [MRD](MRD.md) · [SRS](SRS.md) · [DESIGN](DESIGN.md) |

These are **manual** test procedures, not automated tests. This repository's sandbox runs under
WSL2, which cannot reach real LAN broadcast/HTTPS devices (see `CLAUDE.md`'s "WSL2 can't reach real
UDP-broadcast devices" gotcha — the same networking limitation applies here) — so every case below
must be run from a real Windows Chrome session against an actual camera/NVR, with the native host
installed (`src/chrome-extension/native-host/README.md`).

| ID | Title | Preconditions | Steps | Expected result |
|---|---|---|---|---|
| TC-1 | Checkbox hidden outside the extension | Load `dist/nodejs/examples/public/` via `npm run start:server` in a browser | Open the served page | `native_tls_proxy_field` (the "Bypass Untrusted Certificate" row) is not visible — `IS_EXTENSION` is false there (FR-2). |
| TC-2 | Checkbox unchecked → unchanged default behavior | Extension loaded unpacked, native host installed, a camera reachable over plain HTTP (or a trusted-cert HTTPS device) | Fill in device fields, leave the new checkbox unchecked, check "Use SUNAPI" | Behaves exactly as before this feature: `SunapiManager.init()` runs via the browser XHR client; no native `httpRequest` messages are sent (verify via the native host process, e.g. temporary logging, or by disconnecting network to the device — the browser's own network tab shows the direct HTTPS/HTTP request, not a native-host round trip). |
| TC-3 | Self-signed HTTPS camera, checkbox checked, happy path | A camera/NVR with a self-signed HTTPS certificate on the LAN; confirmed to fail with `ERR_CERT_AUTHORITY_INVALID` when checkbox is off | Enter the device's HTTPS URL/credentials, check "Bypass Untrusted Certificate (Native Host)", check "Use SUNAPI" | The checkbox stays checked (no `.catch()` popup), the video source/profile panels populate, `Play` becomes usable — matching a normal successful SUNAPI session against a trusted device. |
| TC-4 | Digest auth success | Same device as TC-3, valid credentials | Run TC-3 | The native host's Digest challenge/response round completes transparently — the extension only ever sees one final `httpResponse`, not an intermediate 401 (FR-5). |
| TC-5 | Digest auth failure (wrong password) | Same device as TC-3, deliberately wrong password | Run TC-3 with a bad password | `initSunapiManager()`'s `.catch()` fires with a `SunapiError`-shaped popup (`Error Code:`/`Error:`), same as a normal auth failure against a trusted device — not a native-host crash or an unhandled rejection. |
| TC-6 | Non-private-IP URL rejected | Any device entry, checkbox checked | Set the device hostname to a public IP or a DNS name instead of a LAN IP literal, attempt to connect | The native host refuses the request (`httpError`, "refusing to proxy to..."); no HTTPS request is attempted to that host (NFR-2). Confirms the IP-literal allowlist, not just that public hosts happen to be unreachable. |
| TC-7 | Native host not installed | Extension loaded, native host **not** registered (or `com.wisenet.ipinstaller.json` removed) | Check the new checkbox, attempt to connect | `chrome.runtime.connectNative()` fails; the resulting rejection surfaces through the same `.catch()` path as TC-5 (a readable error, not a silent hang or an uncaught exception). |
| TC-8 | Switching devices closes the previous native port | Two devices, both requiring the native proxy | Connect to device A with the checkbox checked, then select device B and connect again with the checkbox checked | No stale connection/leaked port from device A's `NativeSunapiClient` — verify via the native host process list, or that device B's requests aren't answered using device A's stale in-flight state (NFR-5; `window.ts` closes and replaces `nativeSunapiClient` on each `initSunapiManager()` run). |
| TC-9 | `npm run build` still produces both targets | Clean checkout | `npm run build` | Succeeds for both `dist/chrome-extension/` and `dist/nodejs/`; the nodejs target's `window.html` contains the checkbox markup but it stays hidden per TC-1 (one shared `window.html`/`window.ts` build, per `../architecture.md`). |
| TC-10 | Streaming succeeds over `wss://` with the checkbox on | Same device as TC-3, an H.264/H.265 channel (not MJPEG — canvas rendering has its own unrelated codec-driven behavior, see `MEMORY.md`) | Run TC-3, then press Play | Video actually renders — confirms `wsOpen`/`wsMessage` round trips are happening (F12 console: `[nativeWebSocketTransport] opening ...` and no `net::ERR_CERT_AUTHORITY_INVALID` on a `wss://` entry in the Network tab's WS filter). |
| TC-11 | Streaming checkbox off → unchanged default `wss://` behavior | Same device as TC-3 | Uncheck the bypass checkbox, attempt Play | Behaves exactly as before this feature: a plain browser `WebSocket` is opened directly (Network tab's WS filter shows it going straight to the camera, not via the native host); fails with the browser's own TLS rejection on a self-signed cert, same as `ws:`-works/`wss:`-fails behavior already observed pre-fix. |
| TC-12 | Stopping playback cleanly closes the native WS connection | Same device as TC-10, stream playing | Press Stop | The native host's `ws` connection to the camera closes (`wsClose` observed in console logs / no orphaned `node.exe` process lingering after the extension's own native port disconnects — see `process.stdin.on('end', ...)`'s cleanup in `wisenet-udp-host.ts`). |
| TC-13 | Non-private-IP `wss://` URL rejected | Checkbox on | Somehow point the stream at a non-LAN host (e.g. a modified `hostname` field) | `wsOpen` is refused (`wsError`, "refusing to proxy to...") before any WebSocket handshake is attempted — same allowlist as TC-6, now also covering the streaming path (SRS FR-10). |
| TC-14 | Switching devices doesn't leak the previous stream's native port | Two devices, both playing over the bypass path | Play device A, Stop, select device B, Play | No leaked `node.exe`/native port from device A's stream — each `NativeWebSocketLike` instance owns and disconnects its own port on `close()`/`wsClose`. |
